# ПОС — Преподавательская Оценка Студентов

Консольный модуль учёта преподавательских оценок студентов, разработанный на Python с применением **Domain-Driven Design (DDD)**, архитектуры **Ports & Adapters (Hexagonal)**, **паттернов GoF** и **DI-контейнера**.

---

## 1. Архитектура и слои

В проекте реализована облегчённая **Ports & Adapters (Hexagonal Architecture)** с направлением зависимостей строго внутрь — к доменной модели.

```text
+-------------------------------------------------------------------+
|                   Composition Root (services/)                    |
|                          container.py                             |
+---------------------------------+---------------------------------+
                                  | собирает граф зависимостей
                                  v
+-------------------------------------------------------------------+
|                 Infrastructure / Adapters                         |
|  persistence.py (InMemory Repos, CSV/JSON Exporters)              |
|  console_ui.py  (POSFacade, ConsoleUI)                            |
+---------------------------------+---------------------------------+
                                  | зависит от портов и Use Cases
                                  v
+-------------------------------------------------------------------+
|                   Application / Use Cases                         |
|  use_cases.py (Student/Criterion/Evaluation/Report UseCases,      |
|                DTO, исключения, порт ReportExporter)              |
+---------------------------------+---------------------------------+
                                  | оркестрирует доменную модель
                                  v
+-------------------------------------------------------------------+
|                     Domain (Ядро системы)                         |
|  value_objects.py (Score, Weight)                                 |
|  entities.py      (Student, Criterion, Evaluation + Factory)      |
|  repositories.py  (Абстрактные порты репозиториев)                |
|  services.py      (TotalScoreCalculator + Strategy)               |
+-------------------------------------------------------------------+
```

**Стрелка зависимостей:** `services (Composition Root)` -> `infrastructure` -> `application` -> `domain`.

Слой `domain/` использует исключительно стандартную библиотеку Python (`abc`, `dataclasses`, `datetime`, `typing`, `uuid`) и не зависит от консоли, файловой системы, CSV/JSON или сторонних фреймворков.

## 2. Карта Domain-Driven Design (DDD)

### Ubiquitous Language (Единый язык предметной области)
* **Student (Студент)** — учащийся курса, которого оценивают.
* **Criterion (Критерий рубрикатора)** — элемент оценивания с названием, максимальным баллом (`max_score`) и вкладом в итоговую оценку (`weight`).
* **Evaluation (Оценка)** — зафиксированный факт выставления конкретного балла студенту по критерию из рубрикатора (с датой выставления и опциональным комментарием).
* **Total Score (Итог)** — вычисляемый результат по студенту, всегда согласованный с текущим набором его оценок и рубрикатором.

### Осознанное разделение Entities и Value Objects
* **Entities** (`Student`, `Criterion`, `Evaluation`) обладают уникальным идентификатором (`UUID`) и собственным жизненным циклом. Например, `Evaluation` можно изменить через метод `update_score()` — оценка сохранит свой `evaluation_id`, но обновит балл и комментарий с повторной проверкой инвариантов.
* **Value Objects** (`Score`, `Weight`) реализованы как неизменяемые `@dataclass(frozen=True)`. Они не имеют идентификатора, сравниваются по значению и гарантируют собственную валидность при создании в `__post_init__` (`Score.value >= 0`, `0 < Weight.value <= 1`).

### Границы агрегатов
В рамках ядра системы `Student`, `Criterion` и `Evaluation` выделены как отдельные корни агрегатов, связанные по идентификаторам (`student_id`, `criterion_id`). Такое решение позволяет независимо добавлять студентов, формировать рубрикатор и выставлять/исправлять/отменять оценки без загрузки в память всей сущности курса на каждую операцию. В дальнейшем это упрощает масштабирование под несколько курсов, пересдачи и апелляции.

### Инварианты предметной области
1. **Неотрицательность балла:** `Score` не допускает значения меньше `0`.
2. **Граница критерия:** балл не может превышать `criterion.max_score` ни при создании оценки (`Evaluation.create`), ни при её исправлении (`Evaluation.update_score`).
3. **Валидность рубрикатора:** `max_score > 0` (`Criterion`), `weight ∈ (0, 1]` (`Weight`), названия критериев уникальны, а суммарный вес рубрикатора не превышает `1.0` (`CriterionUseCases`).
4. **Оценка только по существующему критерию:** `EvaluationUseCases` блокирует выставление оценки по отсутствующему критерию или студенту, а также запрещает дублирование оценки по одной паре `(student_id, criterion_id)`.
5. **Согласованность итога:** итоговый балл не хранится как произвольное поле, а каждый раз пересчитывается в `TotalScoreCalculator` на основе актуальных оценок и критериев.

### Порты (Repositories и Exporter) и Domain Service
* **Порты хранилищ (`domain/repositories.py`):** `StudentRepository`, `CriterionRepository`, `EvaluationRepository` задают контракты доступа к данным внутри домена. Их реализации (`InMemory*Repository`) находятся в `infrastructure/persistence.py`.
* **Порт экспорта (`application/use_cases.py`):** `ReportExporter` отделяет сценарий выгрузки ведомости от конкретного формата файла (`CsvReportExporter`, `JsonReportExporter`).
* **Domain Service (`domain/services.py`):** `TotalScoreCalculator` инкапсулирует расчёт итога, так как это правило зависит одновременно от множества оценок студента и всего рубрикатора и не принадлежит одной сущности.

## 3. Обоснование паттернов GoF

В проекте применено по одному паттерну из каждой группы GoF — каждый решает конкретную задачу архитектуры или домена:

| Группа | Паттерн | Где реализован | Какую боль закрывает |
| :--- | :--- | :--- | :--- |
| **Порождающие** | **Factory Method** | `Evaluation.create()` в `domain/entities.py` | Создаёт единую контролируемую точку инстанцирования `Evaluation`, где проверяется инвариант `0 <= score <= criterion.max_score` и связь с объектами `Student` и `Criterion`. |
| **Структурные** | **Facade** | `POSFacade` в `infrastructure/console_ui.py` | Слой `application/` разбит по принципу единственной ответственности (SRP) на 4 независимых класса (`StudentUseCases`, `CriterionUseCases`, `EvaluationUseCases`, `ReportUseCases`). Фасад скрывает их оркестрацию и переключение стратегий за единым удобным API для консольного интерфейса. |
| **Поведенческие** | **Strategy** | `CalculationStrategy`, `WeightedSumStrategy`, `NormalizedTenPointStrategy` в `domain/services.py` | Выносит формулу расчёта итога из `TotalScoreCalculator` в сменные стратегии (прямая взвешенная сумма и приведение критериев с разным `max_score` к 10-балльной шкале). Новые правила расчёта добавляются без изменения доменного сервиса (OCP). |

## 4. DI-контейнер и логика сборки

В `services/container.py` реализован `DIContainer` с поддержкой `register_singleton` и `register_transient`, а функция `build_container(export_format, strategy_name)` выступает точкой сборки (`Composition Root`):

* связывает абстрактные порты репозиториев с их in-memory адаптерами;
* подставляет выбранный адаптер экспорта (`CsvReportExporter` или `JsonReportExporter`) в `ReportExporter`;
* внедряет начальную стратегию расчёта в `TotalScoreCalculator`;
* собирает Use Cases, `POSFacade` и `ConsoleUI`.

Благодаря этому подмена формата выгрузки (CSV <-> JSON) или хранилища выполняется в одном месте на краю приложения без единой правки в домене или сценариях.

## 5. Запуск приложения и тестов

Требуется **Python 3.9+**, сторонние библиотеки не используются. Все команды выполняются из корневой директории `HW2/`:

```bash
# Интерактивный консольный режим (полное меню + пункт 12 для сквозной демонстрации)
python3 main.py

# Прямой прогон сквозного демонстрационного сценария с экспортом в CSV
python3 main.py --demo

# Прогон сквозной демонстрации с экспортом в JSON (демонстрация подмены адаптера в DI)
python3 main.py --demo --format json

# Запуск юнит-тестов на инварианты, Domain Service, Use Cases и экспорт
python3 -m unittest discover -s tests -v
```

### Что проверяет сквозной сценарий (`--demo`)
1. Добавление студентов и формирование рубрикатора критериев с разными `max_score` и весами.
2. Выставление корректных оценок с комментариями.
3. Попытки нарушить инварианты (дубликат оценки, выставление 12 баллов из 10, оценка по несуществующему критерию) и их перехват.
4. Исправление выставленной оценки с пересчётом итога.
5. Расчёт итоговой ведомости по обеим стратегиям (`WeightedSumStrategy` и `NormalizedTenPointStrategy`).
6. Экспорт итоговой ведомости в файл (`.csv` или `.json`).

## 6. Роль ИИ в решении

* **Роль ИИ-помощника:** Помощь в поэтапной проработке слоёв архитектуры (`domain`, `application`, `infrastructure`, `services`), генерация шаблонного кода (DTO, адаптеры экспорта CSV/JSON, интерактивное консольное меню, DI-контейнер) и написание набора юнит-тестов (`tests/test_pos.py`).
* **Что сделано и переработано самостоятельно:**
  * Проектирование целевой структуры проекта под Ports & Adapters и отказ от минималистичного прототипа в пользу послойной проработки, чтобы избежать анемичной доменной модели;
  * Выбор стека на чистой стандартной библиотеке Python (`abc`, `dataclasses`, `typing`, `unittest`, `csv`, `json`, `argparse`) без сторонних зависимостей с учётом совместимости с Python 3.9+;
  * Проработка доменных правил и разделения ответственности между `Value Objects` (`Score`, `Weight`), сущностями (`Evaluation.create` / `update_score`), сценариями (`UseCases`) и тремя паттернами GoF (`Factory Method`, `Facade`, `Strategy`);
  * Сборка проекта, настройка пакетов и устранение проблем с импортами и регистром файлов в окружении macOS;
  * Прогон и верификация всех 19 юнит-тестов, сквозных демо-сценариев с выгрузкой в CSV и JSON, а также ручное тестирование интерактивного консольного меню и граничных случаев валидации (пустой ввод, выход веса за границы `(0, 1]`, дробный ввод через запятую, отмена оценки с пересчётом итога, смена стратегий).
